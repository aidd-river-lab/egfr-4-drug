# 跟着两个真实分子走一遍全流程(慢速、详细版)

[10-pipeline-walkthrough.md](10-pipeline-walkthrough.md)是按"架构层级"讲的——
每一层做什么、黑盒打分函数背后是什么算法。如果你读完那篇还是觉得抓不住，
问题通常不是内容太难，是"按模块讲"这个顺序本身对第一次接触的人不友好——
你没有一个具体的、完整的"案例"可以从头跟到尾。

这篇换一种讲法：**全程只跟两个真实分子**，每一步都是这两个分子在这一步
真实发生的事情，用这个仓库里真实跑出来、真实存在数据库/文件里的数字，
不用占位符、不用"假设分子X"。遇到任何术语，当场解释，不留到后面。

两个主角：

- **RTC-0000**——这个仓库自己从骨架+R基团**生造出来**的一个分子，SMILES是
  `Cc1ccc(-c2ccnc(Nc3ccc(S(C)(=O)=O)cc3)n2)c(N2CCOCC2)c1`。它不是凭空选的
  例子，它是路线C那一轮发现流程里**真实跑出来排第一名**的分子(在数据库
  `decision_batch_members`表里能查到：`batch_role=exploit`,
  `is_pareto_optimal=1`, `desirability_score=1.0`)。跟着它能看到"一个分子
  从不存在，到被造出来，到被初步认为还不错"的完整过程。
- **奥希替尼(osimertinib)**——真实上市药物，SMILES是
  `COc1cc(N(C)CCN(C)C)c(NC(=O)C=C)cc1Nc1nccc(-c2cn(C)c3ccccc23)n1`
  (这个SMILES在`tests/test_standardize.py`里被验证过，算出来的InChIKey
  `DUYJMQONPNNFPI-UHFFFAOYSA-N`和真实公开数据库对得上，不是凭记忆编的)。
  跟着它能看到"已经知道真实答案的分子，在这个仓库的流程里跑出来的数字是不是
  靠谱"——这是一种叫**回顾性验证(retrospective validation)**的检验方法，
  [doc/11](11-industrial-gap-and-roadmap.md)里提到的"用已知答案检验方法"
  就是这个思路的延伸(只不过那边用的是上百个分子统计出AUC，这里只是先拿
  一个你熟悉的分子对对账，建立直觉)。

## 第〇步：一个分子在电脑里到底是什么

在讲流程之前，必须先搞懂一件事：计算机里根本没有"分子"这个东西，只有
**文本字符串**和**数字**。所有后面的步骤，本质上都是对一个字符串反复做
"解析 → 变换 → 再变成另一个字符串/一组数字"。

### SMILES：用文字描述一个分子的"装配说明书"

`*C`是什么？这是本仓库R基团库里"methyl(甲基)"这个片段的真实写法
(`routes/route_c_4th_gen_tki/config/rgroup_libraries/pocket_regions.yaml`
第48行)。逐个字符看：

- `C`：一个碳原子。SMILES里大写字母是元素符号(C=碳，N=氮，O=氧，S=硫)。
- `*`：一个"连接点"占位符，表示"这里还有一根化学键伸出去，连去哪还没定"。

再看一个复杂点的：`*S(C)(=O)=O`(entrance_797区域的methylsulfone/甲基磺酰基
片段)：

- `S`：硫原子
- `(C)`：括号表示"分支"——S原子除了主链方向的键，还连了一个碳(甲基)
- `=O`：双键连一个氧
- 再一个`=O`：又双键连一个氧
- 所以这整个片段是：一个连接点 + 硫原子，硫原子上挂一个甲基、两个双键氧——
  这就是"甲基磺酰基"(-SO₂CH₃)的真实化学结构，SMILES只是用文本把这个结构
  描述出来。

**小写字母表示"芳香原子"**(芳香环，比如苯环那种电子高度共享、特别稳定的环
结构)：RTC-0000的SMILES里`c1ccc(...)c(...)c1`这一段，`c`是小写，表示这是
一个苯环上的碳(大写`C`是普通碳)。环的"闭合"靠数字配对——两个标了同一个
数字(比如两个`1`)的原子之间有一根键，把这个环首尾连起来。

**这件事的重要性**：SMILES是一种**只描述"谁和谁连在一起、连接方式是什么"
的拓扑结构**，完全不包含三维空间坐标——不知道这个分子在空间里长什么形状、
哪个原子在哪个位置。这是为什么后面"对接"这一步之前，必须先有一个单独的
步骤把SMILES"生成"出一个真实的三维构象(这件事由RDKit的`AllChem.EmbedMolecule`
完成，本质是从一堆物理上合理的候选三维形状里采样一个出来，这不是本文重点，
但你要知道"文本"和"三维形状"是两件完全不同的事，中间有一道真实的计算步骤)。

### 分子指纹/描述符：把分子变成数字

后面要给分子"打分"、"比较"，但计算机没法直接比较两个字符串谁"更好"——
所以几乎每一步都会先把分子变成一组**数字**(比如"分子量"就是把所有原子的
原子质量加起来，这是最简单的一种描述符)，这组数字才是真正被公式/算法
处理的东西。记住这个转换关系：**SMILES字符串 → 数字描述符/三维坐标 →
参与计算**，贯穿整个流程。

## 第一步：骨架+R基团怎么拼出RTC-0000

RTC-0000不是手写出来的，是程序从一个**骨架模板**和三组**候选片段**的
笛卡尔积组合里生成的。真实配置(来自`routes/route_c_4th_gen_tki/config/
rgroup_libraries/scaffolds.yaml`)：

```
骨架核心: [1*]c1ccc(Nc2nccc(-c3ccc([2*])cc3[3*])n2)cc1
```

这是一个"留了三个坑"的分子——`[1*]`、`[2*]`、`[3*]`是三个待填的连接点，
数字`1`/`2`/`3`不是环编号，是**同位素标记**，专门用来给连接点"贴名字标签"
(真实化学里这类标记叫同位素标记原子，这里借用这个机制纯粹是当"具名参数"用，
和真实的放射性同位素没有关系)。三个坑分别对应三个口袋区域：

| 坑 | 口袋区域 | RTC-0000实际填的片段 | 片段真实SMILES |
|---|---|---|---|
| `[1*]` | entrance_797(797入口区) | methylsulfone(甲基磺酰基) | `*S(C)(=O)=O` |
| `[2*]` | hydrophobic_back_pocket(疏水背袋) | methyl(甲基) | `*C` |
| `[3*]` | solvent_exposed(溶剂暴露区) | morpholine(吗啡啉环) | `*N1CCOCC1` |

`core/enumerate.py`要做的事，就是把骨架里的`[1*]`换成methylsulfone、
`[2*]`换成methyl、`[3*]`换成morpholine，三个片段各自的`*`和骨架对应位置
的`[N*]`**互相"焊接"**成一根正常的化学键(这个焊接操作的技术名字是
**molzip**，RDKit提供的一个专门函数)。焊完之后，三个标记(连接点`*`)全部
消失，变成一个完整、正常、没有任何"坑"的分子——这正是RTC-0000真实的
SMILES：

```
Cc1ccc(-c2ccnc(Nc3ccc(S(C)(=O)=O)cc3)n2)c(N2CCOCC2)c1
```

你可以在这个最终SMILES里找到三个片段的痕迹：最前面的`C`(methyl的碳)、
中间的`S(C)(=O)=O`(methylsulfone)、末尾的`N2CCOCC2`(morpholine的六元环，
里面一个氧一个氮)——它们原来各自的`*`标记都已经变成了真正的化学键，
看不出"焊接缝"，这正是molzip拼接成功的标志。

**为什么要在这一步做"连通性校验"**：如果拼接逻辑写错了(比如把两个片段
的连接点焊到了彼此身上而不是焊到骨架上)，RDKit不一定会报错，可能会算出
一个"看起来合法但其实是两个互不相连的碎片硬凑在一个SMILES字符串里"的
结果。`core/enumerate.py`每拼完一个分子都用`Chem.GetMolFrags()`数一下
"这个分子实际是几块"，必须是1块才收进候选池——这是本仓库踩过的真实坑，
不是预防性的过度设计。

**这一步产出的是一整批候选**，不是只有RTC-0000——entrance_797区域有3个
备选片段、hydrophobic_back_pocket有3个、solvent_exposed有若干个，三者
做笛卡尔积，这一轮实际枚举出了几十到上百个候选分子，RTC-0000只是其中
编号第0号的那一个(后面会看到它为什么能在这么多候选里排到第一)。

## 第二步：标准化——为什么同一个分子不能有两种写法

拼接出来的SMILES要过一遍`core/standardize.py`，这一步要解决一个问题：
**同一个分子可以用无数种不同的SMILES字符串写出来**(从哪个原子开始写、
往哪个方向绕，都能生成不同字符串，但描述的是同一个分子)。如果不统一，
后面"查重"(这个分子是不是已经出现过了)这件事根本做不了——就像同一个人
的身份信息，有人写"张三"有人写"张 三"有人写曾用名，不先统一格式，查重
系统永远查不出这是同一个人。

标准化做三件事：

1. **脱盐**：如果分子带着一个反离子(比如盐酸盐里的Cl⁻)，去掉，只留
   药理活性的母核部分。
2. **归一化**：把同一个分子的不同"互变异构体"写法统一成一种。
3. **算规范SMILES + InChIKey**：RDKit内部给每个原子算一个唯一排序，
   按这个顺序重新写SMILES，保证同一个分子永远得到同一个字符串；
   **InChIKey**是另一套独立的、IUPAC(国际纯粹与应用化学联合会)官方标准
   算法，产出一个27字符的定长编码，本仓库拿它当"分子的身份证号"去重。

奥希替尼真实跑一遍这个流程：

- 输入：`COc1cc(N(C)CCN(C)C)c(NC(=O)C=C)cc1Nc1nccc(-c2cn(C)c3ccccc23)n1`
- 规范化输出：`C=CC(=O)Nc1cc(Nc2nccc(-c3cn(C)c4ccccc34)n2)c(OC)cc1N(C)CCN(C)C`
  (注意：和输入字符串完全不一样，但RDKit解析出来是同一个分子——这正好
  证明了"字符串不唯一"这件事是真的)
- InChIKey：`DUYJMQONPNNFPI-UHFFFAOYSA-N`——这个值和公开化学数据库里
  奥希替尼真实登记的InChIKey完全一致，`tests/test_standardize.py`里有一条
  测试专门锁定这件事，防止以后改坏了还不知道。

## 第三步：ADMET画像——给分子做体检

这一步给每个标准化后的分子算一组**物理化学描述符**，可以理解成"体检报告
上的各项指标"——每一项单独看意义有限，但整体画像能大致判断这个分子"能不能
吃下去、会不会在体内出问题"。两个分子真实的体检报告：

| 指标 | 含义 | RTC-0000 | 奥希替尼(真实上市药) |
|---|---|---|---|
| MW(分子量) | 整个分子有多重，太大通常口服吸收差 | 424.53 | 499.62 |
| cLogP | 亲脂性(越高越"油"，越容易穿细胞膜，但太高容易脱靶/毒性) | 3.44 | 4.51 |
| TPSA | 极性表面积，和细胞膜/血脑屏障穿透能力负相关 | 84.42 | 87.55 |
| HBD/HBA | 氢键供体/受体数量，影响溶解度和膜穿透 | 1 / 7 | 2 / 8 |
| CNS MPO | 综合打分(0-6)，衡量"适合做中枢神经系统药物"的程度 | **4.6(通过4.0门槛)** | **2.25(没通过)** |
| hERG风险代理 | 心脏钾离子通道毒性的粗略预警 | low | high |

**最值得注意的一行是CNS MPO**：按这个仓库自己的打分公式，RTC-0000反而
"看起来"比真实上市、真实在临床使用的奥希替尼更适合做中枢神经系统药物。
这不代表RTC-0000真的更好，恰恰相反——这是一次很好的"模型局限性"现场
教学：

1. CNS MPO本身只是6个简单物理化学描述符的加权打分，不是真实穿透血脑
   屏障实验的替代品，公开文献里确实记录过奥希替尼"体外活性好但CNS穿透
   不算顶尖"，这一点和真实情况方向是对的；
2. 但奥希替尼真实的临床数据远比一个简单打分公式复杂(真实给药剂量、
   真实血脑屏障转运蛋白的相互作用，这些都不在6个描述符的计算范围内)；
3. `core/admet.py`模块文档里专门标注了`clogd_approx`直接复用`clogp`这个
   已知局限(没接pKa预测器，没法区分中性分子和真实生理pH下的电离态)——
   这是为什么doc/11说"这把尺子的精度有边界，不能直接当真实实验数据用"。

**这不是在为这个仓库的模型护短**，恰恰是在演示它遵守的那条原则：所有计算
出来的数字老实展示，不因为和"常识"(真实上市药应该分数更高)不一致就偷偷
调整或者隐藏——数字背后的局限性写在文档里，让使用者自己判断能不能信。

## 第四步：结构警示——奥希替尼为什么会被标记

`run_structural_alerts()`用一组**SMARTS模式**(SMILES的"查询语言"版本，
作用类似正则表达式，但匹配的是分子子结构而不是文本)去扫描分子里有没有
已知的高风险化学基团。真实跑一遍奥希替尼：

```
alert_verdict: OPTIMIZE_NEEDED
命中规则: michael_acceptor_offtarget
```

**这个警示命中是完全正确、符合预期的**，不是误报：奥希替尼的作用机制
正是靠分子里的丙烯酰胺基团(SMILES里的`C=C`+`C(=O)`那一段)去跟EGFR口袋
里的Cys797发生化学反应、形成永久共价键("焊死"在口袋里，详见
[learning-guide.md](learning-guide.md)第3.1节)。这个丙烯酰胺基团化学上
正是一个**迈克尔受体(Michael acceptor)**——这类基团的通病是它不一定只跟
你想要的那个半胱氨酸反应，可能跟体内别的蛋白质上意外出现的半胱氨酸也
反应(脱靶毒性)，所以结构警示规则库会把它标记出来提醒"这是一个需要谨慎
评估反应性的基团"。

但警示等级是`OPTIMIZE_NEEDED`(需要优化关注)，不是`REJECT`(直接拒绝)——
因为这个仓库的规则库明确知道"共价抑制剂的弹头本身就是迈克尔受体，这是
设计意图，不是意外缺陷"，所以`config/structural_alerts.yaml`给这类规则
配了**豁免清单机制**：如果分子被明确标注为"走共价路线"，这条警示会降级
而不是直接把整个分子拒绝掉。这正是[doc/00](00-design-overview.md)原则3
"规则要有豁免清单，且豁免清单要有验证过的正负对照"的真实体现——
`tests/test_structural_alerts.py`里专门有测试锁定"奥希替尼在豁免开启/
关闭两种情况下分别应该拿到什么判定"，防止以后改规则的时候把这个关键的
豁免逻辑改坏。

RTC-0000没有触发任何警示(这一轮发现流程里，`structural_alert_hits`这张
落库的表是空的——这一批demo候选里没有任何分子命中任何警示规则，这是
诚实的真实统计结果，不是漏统计)。

## 第五步：蛋白质口袋和对接——数字-7.91到底是什么意思

前面几步都只处理"分子本身"，没碰蛋白质。这一步要回答真正核心的问题：
**这个分子能不能钻进EGFR的口袋、结合得牢不牢**。

### 口袋是什么，怎么定义

EGFR的三维结构来自真实下载的晶体结构(PDB编号6LUD，一种实验方法——
X射线晶体学——测出来的真实蛋白质原子坐标文件)。"口袋"不是一个抽象概念，
是蛋白质表面一个真实的三维凹陷区域，由一组氨基酸残基的侧链围成。本仓库
定义口袋的方式是：找到已知能结合在这个口袋里的某个配体(比如晶体结构里
共结晶的真实抑制剂)，算出它所有原子坐标的几何中心，拿这个中心点当对接
搜索框的**中心**，再划定一个边长20多Å(埃，1Å=10⁻¹⁰米，大约是一个碳-碳
单键长度的7倍)的立方体盒子当搜索**范围**——对接算法只在这个盒子内部搜索
配体的摆放方式，不会漫无目的地搜索整个蛋白质表面。

### 对接算法在搜索什么

给定一个配体的三维构象(还记得第〇步说的，SMILES要先生成三维坐标)，
对接程序(这里用AutoDock Vina)要在"盒子内部的位置 × 配体整体的朝向 ×
配体每根可旋转键各自的扭转角度"这个高维连续空间里，找一个让**打分函数**
最优的组合——这是一个数学上的**全局优化问题**，Vina用的是"随机生成起点
→ 局部梯度下降找附近的最优点 → 概率性接受/跳到下一个随机起点 → 重复很多
次取全程最优"这套启发式搜索(更详细的算法说明见[doc/10第4节](
10-pipeline-walkthrough.md#4-深入vina对接分数到底是怎么算出来的))。

### 打分函数算出来的"kcal/mol"是什么意思

真实跑出来的数字：

- 奥希替尼重新对接回6LUD口袋：**-7.758 kcal/mol**(验证文件：
  `routes/route_c_4th_gen_tki/structures/osimertinib_redocked.pdbqt`)
- RTC-0000对接到C797S三重突变体系(T790M+L858R+C797S)：**-7.91 kcal/mol**
- RTC-0000对接到C797S主要基因型模型(PyRosetta计算突变产出)：
  **-7.98 kcal/mol**

单位kcal/mol(千卡/摩尔)是能量单位，**负数表示"结合是有利的"**，数值越负
表示打分函数认为结合越强。但这个数字不是凭空的——它背后对应着一个真实的
热力学关系式：

```
ΔG = -RT·ln(Ka)
```

`ΔG`是结合自由能(就是这个kcal/mol数字)，`R`是气体常数(1.987×10⁻³
kcal/(mol·K))，`T`是温度(体温/室温常取298K)，`Ka`是结合平衡常数(越大
表示结合越牢)。把这个公式倒过来，可以把"两个分数相差多少"直接翻译成
"结合强度相差几倍"：

```
倍数 = exp(ΔΔG / (R·T))
```

代入R·T ≈ 0.592 kcal/mol(298K下)：**每相差1个kcal/mol，结合强度大约相差
5.4倍**(exp(1/0.592)≈5.41，这是真算出来的，不是拍脑袋估的整数)。按这个
关系，RTC-0000对两个不同基因型的打分相差0.07 kcal/mol(-7.91 vs -7.98)，
换算成倍数只有约1.13倍(exp(0.07/0.592)≈1.13)——**几乎没有差别，这是噪音
级别的波动，不是真实的选择性信号**。这正好印证了
[doc/10](10-pipeline-walkthrough.md)反复强调的那条红线：Vina打分函数本身
的误差量级(±2.5 kcal/mol)远大于这种0.07的差值，**这一级打分只能用来把
明显不行的分子筛掉，不能拿来在"还不错的候选"之间排座次**——0.07的差别
完全淹没在方法本身的噪声里。

## 第六步：多目标决策——RTC-0000为什么能排第一

这一步面对的是一个几乎所有工程决策都会遇到的问题：**好几个指标同时要
兼顾，而且经常互相矛盾**(比如亲脂性高一点，膜穿透可能变好但毒性风险
也升高)。本仓库的真实做法是**找Pareto前沿**，先用一个和分子/药物完全
无关的例子建立直觉：

假设你在挑笔记本电脑，只看两个指标：价格(越低越好)、电池续航(越长
越好)。

| 型号 | 价格 | 续航 |
|---|---|---|
| A | 5000元 | 8小时 |
| B | 8000元 | 12小时 |
| C | 9000元 | 8小时 |

C被A**支配(dominated)**了——A比C便宜，续航还一样，C没有任何一项比A强，
**C应该被直接淘汰，不需要考虑任何权重**。A和B之间没有谁支配谁(A更便宜
但B续航更好)，这两个都留在**前沿**上，到底选A还是B取决于你个人更看重
价格还是续航——这是一个真实的权衡，算法不该帮你偷偷做这个主观决定。

真实数据上，RTC-0000在这一轮决策只看两个指标：CNS MPO(越高越好)和
SA score(合成难易度，越低越容易，所以是越低越好)。它的真实值是
`cns_mpo=4.6`，`sa_score=2.33`——这一批候选里没有任何其他分子同时在
这两项上都比它更好，所以它留在Pareto前沿上(`is_pareto_optimal=1`)。

**desirability_score为什么恰好是1.0**：这一步在Pareto前沿内部进一步
排序，用的是**几何平均**而不是加权算术平均——这是故意的设计选择。几何
平均下，任何一项指标是0分，总分直接归零(乘法关系里只要有一个因子是0，
结果就是0)；算术平均做不到这件事，一项满分能把另一项的0分硬生生平均
拉起来。CNS MPO=4.6超过4.0这个门槛被判定为"满分"，SA score=2.33低于
3.0这个门槛也被判定为"满分"，两项都是满分，几何平均自然还是满分1.0。

**老实说清楚这个1.0分意味着什么、不意味着什么**：它只说明"在这一轮考察
的这两个相对便宜的指标上，这个分子没有明显短板"，**完全没有涉及它在
EGFR口袋里结合得牢不牢**(那是环节4对接的事，属于不同的、更贵的打分
维度，本仓库的`run_discovery_round.py`默认工作流完全没跑那一段，RTC-0000
后来的对接分数是另一次手动补充验证时才跑出来的，这是两次独立的计算，
不要误以为"desirability=1.0"这个分数本身包含了对接结果)。这正是多目标
决策里最容易被误解的一点：**一个分子在决策阶段拿到满分，只代表它在当时
被纳入计算的那些指标上没有短板，不代表它已经被证明是一个好药**。
