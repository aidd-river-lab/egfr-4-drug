## 1. 整体架构：三层，谁依赖谁

```
routes/<route_id>/config/*.yaml   <- 纯数据，没有一行逻辑代码
        │  (被core/route_config.py指向)
        ▼
core/*.py                          <- 共享计算引擎，16个模块，不知道自己在被哪条路线用
        │  (被workflows/编排调用顺序)
        ▼
workflows/run_*.py                 <- 按固定顺序调用core/*.py，组装成一轮完整的DMTA循环
        │  (可选persist=True)
        ▼
db/*.py + schema                   <- 落库，供下一轮DMTA回顾/跨路线对比
```

这是一个标准的**依赖倒置**设计，和你写后端服务时"业务逻辑不应该依赖具体数据库
实现"是同一个思路：`core/decide.py`里的Pareto计算完全不知道自己在算SHP2还是
EGFR的分子，它只认`DataFrame`里的列名。路线专属的东西(口袋坐标、基因型、
TPP阈值)全部活在`routes/<id>/config/*.yaml`里，核心代码靠`core/route_config.py`
的一个函数拿到正确的配置目录：

```python
# core/route_config.py 全部内容，36行，整个多路线架构的关键就是这个函数
def route_config_dir(route_id: str = "route_c_4th_gen_tki") -> Path:
    d = ROUTES_DIR / route_id / "config"
    if not d.exists():
        raise FileNotFoundError(...)
    return d
```

每个需要读配置的`core/*.py`函数都接受一个可选的`config_dir`参数，不传就默认
路线C——这保证了"先做好一条路线，再扩展成三条"这个真实的演进路径里，旧代码
和旧测试全程不用改一行。

## 2. 走一遍"纯计算"链路：run_discovery_round.py

这是**唯一一条在你这台笔记本上不需要装任何额外软件、GPU、下载任何结构文件
就能从头跑到尾**的链路。跑一下感受输出：

```bash
.venv/bin/python -m workflows.run_discovery_round
```

内部按顺序发生了什么(对照`workflows/run_discovery_round.py`源码)：

### 2.1 枚举(环节3) —— `core/enumerate.py::enumerate_from_scaffold()`

读`routes/<id>/config/rgroup_libraries/scaffolds.yaml`里的骨架SMILES(带
`[*:1]`这种"同位素标记的虚原子"标出可替换位置)，和`pocket_regions.yaml`里
每个口袋区域允许挂哪些R基团，做笛卡尔积组合，用RDKit的`molzip`把骨架和每个
R基团真正拼接成一个完整分子。

**为什么用同位素标记而不是直接用`[*]`**：如果骨架有两个可替换位置，两个都用
裸的`[*]`，RDKit的拼接函数没法知道哪个R基团该接哪个位置——同位素数字
(`[*:1]`/`[*:2]`)就是给两边"配对用的标签"，这跟你写代码时用具名参数而不是
位置参数避免传错顺序是一个道理。

拼完之后立刻做**连通性校验**(`Chem.GetMolFrags`数一下拼出来的分子是不是
真的连成一整块，不是两个不相连的碎片)——这是这个仓库踩过的真实坑：早期
实现偶尔会拼出"看起来是一个分子，实际是两个不相连片段堆在一个SMILES字符串
里"的结果，RDKit不会报错，只有显式检查片段数才能抓到。

### 2.2 标准化(环节1) —— `core/standardize.py::standardize_batch()`

每个枚举出来的SMILES过一遍：

1. **脱盐**(`rdkit.Chem.SaltRemover`)——去掉反离子(比如盐酸盐里的Cl⁻)，
   只保留药理活性的那部分母核。
2. **互变异构体归一化**——同一个分子可能有多种"质子挪动位置不同但本质是
   同一个东西"的写法(比如酮-烯醇互变)，统一成一个标准形式，否则后面查重会
   把同一个分子误判成两个不同的。
3. **规范化SMILES**(canonical SMILES)——同一个分子有无数种写法的SMILES
   字符串(从哪个原子开始写、往哪个方向写都能生成不同字符串)，RDKit内部用
   **Morgan算法的一个变体**给每个原子算一个唯一的"规范排序号"(基于原子自身
   属性+邻居属性反复迭代传播，类似图同构问题里的"规范标记"算法)，按这个
   顺序重新写SMILES，保证同一个分子永远得到同一个字符串。这是后续用字符串
   或InChIKey做严格去重的前提。
4. **算InChIKey**——另一套独立于SMILES的分子标识算法(IUPAC标准)，这里用来
   做跨批次去重的主键，比直接比较SMILES字符串更抗格式差异。
5. 任何一步失败(比如SMILES语法错误、脱盐后分子碎掉)的分子进"隔离区"
   (`quarantine`)，不是报错中断整批——这是"批处理里单条脏数据不该拖垃圾整条
   流水线"的常规工程做法。

### 2.3 ADMET画像(环节6) —— `core/admet.py`

对每个标准化后的分子算一组描述符(`compute_descriptors`：分子量、cLogP、
TPSA、氢键供体/受体数……全部是RDKit内置的分子描述符计算，纯几何+原子类型
统计，不涉及任何实验数据或机器学习模型)，然后：

- `compute_cns_mpo()`：把6个描述符各自过一个**desirability函数**(每个指标
  自己的"好不好"曲线，比如MW越小越好但超过某个值之后就不再加分了，是个
  分段线性/sigmoid形状的映射)，再**加权求和**成一个0-6分的综合分。
- `estimate_herg_risk_proxy()`：hERG钾离子通道毒性的**代理指标**，不是真实
  实验值也不是训练过的机器学习模型，就是"检测到强碱性胺+高亲脂性这个组合
  就打警告"的规则，模块文档里明确标注了这是代理指标、精度有限。
- `run_structural_alerts()`：读`config/structural_alerts.yaml`(三条路线
  共享，不在`routes/`下)，每条规则是一个**SMARTS子结构匹配模式**(SMARTS是
  SMILES的查询语言版本，相当于分子界的正则表达式)，命中就按规则严重度打
  WARN或REJECT。这整个函数是纯规则引擎，和运行时无关，类似代码里的静态
  lint规则。

### 2.4 多目标决策(环节8) —— `core/decide.py`

两个核心算法：

- **`pareto_front()`**：对每个候选分子，检查是否存在另一个候选在"所有
  关心的指标上都不比它差，且至少一项更好"——如果存在，这个候选被**支配
  (dominated)**，不在前沿上。实现是朴素的O(n²)两两比较(候选数量级在几十到
  几千，不需要上更复杂的O(n log n)算法)。前沿上的点代表"没有免费午餐"的
  真正权衡集合，不是"最优的一个点"而是"最优的一组互相不可比较的点"。
- **`desirability_score()`**：**几何平均**而不是加权算术平均——这是设计上
  刻意的选择。算术平均下，一项指标是0、其他项全是满分，平均下来还有分；
  几何平均下任何一项是0，总分直接归零。对应的现实逻辑是"成药性是乘法关系"：
  一个分子选择性拉满但毒性爆表，不应该靠选择性这一项的高分把总评分拉起来，
  它就是不能用。

### 2.5 落库(可选)

`run(persist=True)`会调`db/repository.py::persist_discovery_round()`，把
这一轮的全部中间结果(枚举数、标准化成功率、隔离区、ADMET全量数据、规则
命中、最终批次)按`db/schema_mysql.sql`定义的表结构写进MySQL。**全量数据都
落库，不只是最终批次**——这是为了让"为什么这个分子最后没被选中"这件事
之后还能查，而不是只留下"赢家"看不到"为什么别的分子输了"。

## 3. 走一遍"结构生物学"链路：从PDB到对接分数

上面这条链路完全不碰蛋白质三维结构。但药效的核心问题——"这个分子能不能
真的钻进口袋、结合得牢不牢"——必须有真实的蛋白质三维坐标才能回答。这条链路
这次会话里真实跑通过(针对路线A的SHP2和路线C的EGFR)，步骤如下：

```
core/structures.py::fetch_pdb()          # 1. 从RCSB下载真实晶体结构(.pdb文本文件)
core/structures.py::clean_chain()        # 2. 只保留需要的链，去掉不需要的HETATM
core/structures.py::mutate_residue()     # 3. (如果目标基因型没有现成晶体结构)用PyRosetta做点突变
.venv310/bin/mk_prepare_receptor.py      # 4. 把清洗后的受体PDB转成Vina需要的PDBQT格式
.venv310/bin/mk_prepare_ligand.py        # 5. 把候选小分子的3D结构转成配体PDBQT
core/docking.py::run_vina_docking()      # 6. 真正跑对接，输出结合能分数+最佳姿态
```

**为什么第4/5步不能跳过，不能直接把PDB文件后缀名改成.pdbqt**：这正是本仓库
反复提到的"姊妹项目踩过的坑"。PDB文件只有原子坐标和元素类型，PDBQT需要额外
的**原子类型细分**(区分芳香碳和脂肪碳、极性氢和非极性氢)、**部分电荷**
(经验公式估算的原子级电荷分布，Vina打分函数的静电项要用)、**可旋转键定义**
(哪些单键在对接搜索时可以自由转动)。这些信息必须靠专门的化学信息学工具
(meeko)真正计算出来，不是文本格式转换。

第1/2步是纯文件IO，在主`.venv`下就能跑；第3/6步需要PyRosetta/Vina，必须用
`.venv310`(原因见`scripts/setup_docking_env.sh`的详细注释)。

## 4. 深入：Vina对接分数到底是怎么算出来的

这是整个仓库里被反复强调"不能当精确数值用，只能用来排除"的一个分数，值得
搞清楚它到底是什么。AutoDock Vina干两件独立的事：

**(1) 打分函数(scoring function)**——一个**经验公式**，不是从头算的量子力学
能量。大致形状是：

```
score = 疏水接触项 + 氢键项 + 静电项 + 配体内部扭转熵惩罚项 + ...
```

每一项前面的权重系数，是用几千个**已知结合能的真实蛋白-配体复合物晶体结构**
做回归拟合出来的——本质上是一个**线性回归/经验势模型**，Vina在用的时候只是
查表+加权求和，不涉及真正的量子化学计算。这意味着：这个分数对"这几千个训练
样本长什么样的结合模式"预测得准，对训练集里没见过的、特殊的结合模式(比如
共价结合、金属配位、罕见的卤键)系统性地算不准。

**(2) 搜索算法**——怎么找到"最佳"的结合姿态(位置+朝向+每根可旋转键的扭转角，
合起来是一个高维连续空间)。Vina用的是**迭代局部搜索(iterated local search)**：
随机生成一个初始姿态 → 用BFGS梯度优化方法局部爬到附近的一个能量低点 → 按
Metropolis准则(模拟退火里的经典接受/拒绝规则，允许概率性地接受比当前更差的
解，避免卡在局部最优)决定要不要跳到下一个随机起点 → 重复很多次，取全程遇到
的最优解。

`exhaustiveness`参数就是"重复多少次独立搜索"——越大越可能找到全局最优，但
线性增加计算时间。这是一个经典的**全局优化问题的启发式解法**，不保证找到
真正的全局最优，这也是为什么同一个分子跑两次`exhaustiveness`不同可能拿到
略有差异的分数。

**结论**：Vina分数是"一个用经验公式+启发式搜索算出来的、专门为相对排序设计
的代理指标"，单位写的是kcal/mol，但不能和真实热力学实验测出的ΔG直接画等号。
这就是为什么`pipeline.yaml`里L1阶段的误差标注是±2.5 kcal/mol这么大(大约
10³倍的平衡常数误差)，只能用来"排除明显不行的"，不能用来"给前十名排名次"。

## 5. 深入：PyRosetta的突变建模和打分

`core/structures.py::mutate_residue()`背后在做两件事：

**(1) 残基替换**——把某个位置的氨基酸身份换掉(比如把苏氨酸换成甲硫氨酸，
T790M)，这一步本身很简单，就是把这个位置的原子坐标清空、换上新氨基酸的
标准几何模板，对齐骨架原子(N/CA/C/O，所有氨基酸这几个骨架原子的相对位置是
固定的)。

**(2) 局部repacking**——真正的技术含量在这。换了身份之后，新氨基酸的侧链
原子朝向是未知的(同一个氨基酸的侧链可以绕着几个化学键旋转，不同旋转角度叫
不同的**rotamer**，侧链占据的空间也不一样)，而且这个新侧链很可能跟周围
原来好好待着的侧链"打架"(原子空间重叠，物理上不可能同时存在)。

PyRosetta的"packer"算法要在一个巨大的组合空间里(`pack_radius`范围内每个
残基都有几十个候选rotamer，残基数乘起来是指数级的组合数)找一个让**全局能量
最低**的rotamer组合——这是个NP-hard的组合优化问题，Rosetta用**模拟退火+
死端消除(dead-end elimination)**的近似算法求解，不保证全局最优，但在实践中
效果很好(这也是整个蛋白质设计/结构预测领域的标准做法，AlphaFold出现之前，
"用Rosetta做蛋白质设计"几乎是行业默认选项)。

**关于打分数值的单位**：`mutate_residue()`返回的`total_score_after_repacking`
来自`pyrosetta.get_fa_scorefxn()`，这是Rosetta的全原子能量函数(REF2015这个
版本)，输出单位是**Rosetta Energy Unit(REU)**——一个经过大量蛋白质结构训练
标定出来的相对打分，不是真实物理意义上的kcal/mol(尽管数值量级接近)。它的
用法和Vina分数类似：**只能在同一个体系内部做相对比较**(比如"突变前比突变后
更稳定")，不能跨体系直接比大小，更不能当成真实自由能去代入别的公式。这也是
为什么本仓库做"突变体结构比原始结构更/更不稳定"的判断时，是拿同一个体系
突变前后的分数相减，而不是孤立地看某一个绝对数值。

## 6. 深入：MD/MM-GBSA/FEP——同一个问题，三种精度换三种价格

这三个方法问的都是"这个分子和蛋白质结合得牢不牢"，但用完全不同的计算代价
换不同的可信度，是整条打分漏斗里从L3到L4的核心。

**分子动力学(MD)**：牛顿力学的逐帧仿真。给定一个初始结构和一个**力场**
(描述每个原子之间相互作用力的经验公式集合，常见如AMBER/CHARMM)，每一步
(典型时间步长2飞秒，10⁻¹⁵秒量级)计算每个原子受到的合力，用牛顿第二定律
更新位置和速度，重复几百万到几十亿步模拟出几十纳秒的真实运动轨迹。这一步
本身**不直接产出一个结合能数字**，产出的是"这个结合姿态在模拟的时间尺度内
稳不稳定"——如果配体在前几纳秒就从口袋里飘出来了，说明这个对接姿态很可能
是假阳性(对接算法找到的局部最优，不是真实稳定的结合模式)。这正是
`core/md_stability.py`的`evaluate_pass_criteria()`在检查的：配体RMSD(相对
初始姿态的均方根偏移)有没有在模拟后期保持低、关键氢键有没有保持高占据率。

**MM-GBSA**：拿到MD轨迹之后，从轨迹里抽样很多帧快照，对每一帧用一个**近似**
的能量公式(分子力学项+广义born/表面积模型估算的溶剂化自由能项)算一个结合
能，再对所有帧取平均。比起直接用MD轨迹做严格的自由能计算(比如热力学积分)，
这是一个精度换速度的近似——丢掉了熵的严格计算(通常用一个简化的准谐近似)，
换来几十分钟就能出一个数，而不是几天。

**FEP(自由能微扰)**：如果你要的不是绝对结合能，而是"分子A改造成分子B，
结合能变化了多少"，FEP给出目前计算化学里能拿到的最精确答案。核心技巧叫
**炼金术路径(alchemical pathway)**：在计算机模拟里引入一个虚拟参数λ(从0到
1)，让体系里的分子A的原子"逐渐"变成分子B的原子(用λ控制相互作用强度的
渐变混合，专门用"软核势"处理λ接近0或1时的原子重叠奇异点)，在每个λ窗口
(典型20-40个窗口)分别跑MD采样，再用统计力学公式(常见Bennett接受比值法，
BAR)把每个窗口的自由能差拼接、累加成总的ΔΔG。这在真实世界里不存在的"分子A
变成分子B"这个过程，只存在于模拟里，所以叫"炼金术"——但背后的统计力学是
严格的，不是比喻。代价是每一对微扰要跑大量MD采样，几个GPU小时起步，这就是
为什么FEP永远是漏斗的最后一级，只对决赛圈的少数分子跑。

`core/fep.py::FEPMapResult.qc_pass()`在做的事和前两者都不同——它不计算FEP，
它检查"算出来的FEP map能不能信"：拿几个已经有**真实实验结合能数据**的化合物
对(叫"锚点")去对比预测值和实测值的误差(MUE，平均绝对误差)，超过阈值就判定
整张map作废。这条规则的重要性在于：**FEP本身的输出永远需要真实实验数据校准
才能判断可信度**，没有实验锚点的FEP结果是不能直接拿去做决策的——这也是本
仓库目前这个环节完全没法跑的根本原因(需要GPU，也需要真实实验数据做锚点，
两者都没有)。

## 7. 深入：路线B三元复合物——Kabsch算法和为什么随机采样找不到解

路线B(降解剂)比前面的抑制剂多一层复杂度：药效取决于**三个分子同时怎么摆放**
(突变EGFR、降解剂、E3连接酶)，不是两个。这次会话真实搭了一个简化版流程，
过程中踩到两个值得理解的算法问题：

**问题1：怎么让配体"跟着"蛋白质的刚体运动，又不用把配体塞进Rosetta的
蛋白质表示系统里？**

Rosetta内部对"一个残基"的表示(原子类型、化学键连接方式、氢加成规则)是围绕
20种标准氨基酸设计的，把一个任意的小分子(降解剂、来那度胺)正确地注册成
Rosetta能识别的"自定义残基类型"涉及不少工程细节(这次探索过`RDMolToRestype`
和`SDFParser`两条路径，都验证了可行但构建完整可用的类型需要更多工作)。

工程上的绕路是：**只对接两个蛋白质链(标准氨基酸，Rosetta原生支持)，把配体
当成外部的"跟随点"，用数学方法让它跟着蛋白质一起动**。具体靠**Kabsch算法**
(经典的刚体配准算法，生物信息学/计算机视觉领域都在用，比如比较两个蛋白质
结构的RMSD对齐也是这个算法)：如果你知道同一组点在"移动前"和"移动后"的坐标，
Kabsch算法能通过对两组点的协方差矩阵做**SVD(奇异值分解)**，精确反推出中间
发生的刚体旋转+平移是什么——然后把这个反推出来的变换，套用在任何你关心的
"外部点"(比如配体的连接原子)上，哪怕这个点本身从没被Rosetta感知过。这是
一个很通用的技巧：**只要知道变换前后同一组参考点的坐标，就能把任何坐标系下
的变换"移植"到另一组完全不相关的点上**。

**问题2：500次随机对接为什么一次都没找到兼容的姿态？**

这次真实跑的结果：均匀随机生成蛋白质朝向、滑到接触为止，重复500次，两个
配体连接点之间的最近距离是26.8Å，而最长的linker也只能连到11.9Å——一次都没
碰上。这不是bug，是**采样策略**的问题：两个蛋白质表面都是三维的球面(可以
理解成两个独立的"随机转向"都是在SO(3)旋转群上均匀取样)，你要求的是"两个
表面上各自一个很窄的点，刚好转到彼此够近的位置"——这是一个概率极低的事件，
纯随机转多少次都大概率撞不上。

真实发表的PRosettaC方法不用随机采样，用**PatchDock**：一种基于**几何形状
互补性打分**的系统性搜索算法，核心思路是把两个蛋白质表面都离散化成"几何特征
补丁(patch)"，用**快速傅里叶变换(FFT)加速的互相关计算**，在所有离散化的
相对平移/旋转组合里快速找出表面形状能"拼"在一起的候选姿态(凹凸互补，像拼
拼图一样有效地剪枝了绝大部分不可能的组合，不需要像随机采样那样盲打)。这正是
`doc/routes/route-b-degrader.md`里记录的那条诚实结论：轻量版(随机采样)在
这个问题上行不通，真实可用的方案需要系统性搜索，不是加大随机次数就能解决的。

## 8. 数据库在整个流程里扮演什么角色

`db/`这一层不是"锦上添花"，是让"多轮DMTA循环"真正成为可能的基础设施。
没有它，每次`run_discovery_round.py`跑完，结果只活在这次进程的内存里，
打印到终端就没了——下一轮没法知道"上一轮哪些分子因为什么原因被拒绝"，
也没法做跨路线、跨轮次的比较。

`db/schema_mysql.sql`定义的18张表基本和10个环节一一对应(`compounds`/
`designed_molecules`对应环节1/3，`funnel_scores`对应环节4，`admet_descriptors`
+`structural_alert_hits`对应环节6，`decision_rounds`+`decision_batch_members`
对应环节8，`wet_lab_results`+`false_positive_attributions`对应环节9)。
`compounds.route_id`这一列是三条路线共用一个库的关键——靠这一列过滤查询，
而不是三套独立的schema，这样"路线A和路线C哪个批次的ADMET画像更好"这种
跨路线分析查询起来很直接。

落库原则(`persist_discovery_round`的docstring)：**全量落库，不只落最终
批次**——因为"为什么这个分子没被选中"本身是有价值的数据，等真实湿实验数据
回来之后(环节9)要拿这些被拒绝的分子去做假阳性归因分析，如果当时只留了
赢家，这个分析根本做不了。
