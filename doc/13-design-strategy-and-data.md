# 设计思路：数据从哪来、分子怎么拼出来、为什么是这三条路线

这篇回答三个你问到的问题：网上抓的数据到底分几类、这些数据后续怎么用、
分子是不是"先定整体骨架再一点点拼"——然后把这些串起来，讲清楚"奥希替尼
耐药之后该怎么设计"这件事背后完整的思考过程，不是罗列数据，是讲清楚
"从数据怎么一步步推导到了现在这三条路线"。

## 1. 网上抓的数据，到底分几类

你的直觉基本对，但要做两处修正——不是"癌细胞数据"，严格说是四类，
而且"结合数据"这一类里藏着一个非常容易搞混、但很关键的区分。

### (1) 靶点结构数据——不是细胞数据，是蛋白质的"三维照片"

真实来源是RCSB PDB(全球蛋白质结构数据库)，本仓库下载过的真实文件：

| PDB编号 | 是什么 | 对应路线 |
|---|---|---|
| 6LUD | EGFR三重突变(L858R/T790M/C797S) + 奥希替尼真实共晶结构 | C |
| 5EHR | SHP2 + SHP099(变构抑制剂)共晶结构 | A |
| 6SCM | SOS1 + BI-3406共晶结构 | A |
| 4TZ4 | CRBN(E3连接酶) + 来那度胺共晶结构 | B |
| (DUD-E egfr receptor，基于PDB 2RGP) | EGFR激酶结构域 | 本次retrospective验证用 |

这些文件是X射线晶体学这种真实实验手段测出来的**蛋白质原子三维坐标**，
你可以理解成"给这个突变蛋白拍了一张分辨率极高的三维照片"，和"癌细胞"
本身没有直接关系——它告诉你的是"这个突变之后的蛋白质口袋长什么形状"，
不是"这个癌细胞有什么其他基因表达特征"。真正意义上的"癌细胞数据"(比如
基因表达谱、细胞系药敏数据)这个仓库**完全没有用到**，这点要纠正一下。

### (2) 化合物数据——两个来源，用途完全不同

- **自建的骨架+片段库**(`routes/<route>/config/rgroup_libraries/*.yaml`)：
  不是下载的，是本仓库自己手写构造的"illustrative_only"候选起点，专门
  用来演示枚举逻辑，见下一节详细讲。
- **DUD-E的真实化合物库**(这次retrospective验证正在用的)：542个真实已知
  对EGFR有活性的化合物(来自ChEMBL) + 35050个"诱饵"分子。**这里有个关键
  区分，容易被误解**：这542个活性分子是真实实验验证过的，但35050个诱饵
  分子**不是**真的拿去测过、确认无效的化合物——它们是按"和活性分子的
  物理化学性质(分子量、亲脂性等)相似，但二维结构刻意选得不一样"这个规则
  **计算挑选**出来的，只是"推测大概率无效"，不是真测出来的阴性结果。
  这是DUD-E这类标准benchmark数据集的通用设计方式(近似真值，不是绝对真值)，
  用于检验方法本身是不是有区分能力已经足够，但如果有人问"这35050个诱饵
  真的一个个测过都不结合吗"，答案是没有，要如实说清楚。

### (3) "两者结合"数据——这是最容易混淆三个不同东西的一类

你说的"结合数据"，真实世界里至少对应三种完全不同的东西，这个仓库目前
分别处于不同的使用阶段：

| 类型 | 是什么 | 这个仓库目前的状态 |
|---|---|---|
| **真实实验结合常数** | 湿实验室测出来的IC50/Ki/Kd，连续数值 | ChEMBL/BindingDB上有大量公开数据，本仓库**查过** E3配体(来那度胺Ki≈3.1μM)的文献值，但还没有系统性批量拉取 |
| **benchmark的二元标签** | DUD-E这种"active/decoy"标签，不是连续数值 | 本次retrospective验证正在用的就是这个 |
| **本仓库自己算出来的对接分数** | Vina跑出来的kcal/mol数字 | 这是**预测值**，不是外部测量值！千万别和上面两种混在一起 |

**第三行是最重要的警示**：`funnel_scores`表里存的那些-7.91/-7.98
kcal/mol，是这个仓库自己的对接程序**算出来的预测**，跟"真实湿实验测出来
这个分子到底结合得牢不牢"是两件完全不同的事——这正是为什么要专门跑一次
retrospective验证：拿第(3)类里第一行(真实测量值，通过DUD-E的"真实活性/
推测无活性"标签间接体现)去检验第三行(我们自己的预测)到底准不准。如果
这两者被混为一谈，会产生一种危险的错觉："算出来的分数=真实结合强度"，
这正是[doc/11](11-industrial-gap-and-roadmap.md)反复强调要避免的。

### (4) 容易被忽略的第四类：患者人群耐药机制的流行病学数据

这一类和具体某个化合物、某个蛋白质结构都无关，是**统计数据**：奥希替尼
耐药之后，病人群体里各种耐药机制分别占多大比例。真实查证过的数字(见
[doc/00](00-design-overview.md)和[competitive-landscape.md](competitive-landscape.md))：

```
C797S突变              约6-7%
MET扩增                约10-15%
HER2扩增               约10-15%
查不出明确基因组驱动因素   约50%
```

这类数据不参与任何一个分子的设计计算，但**它是整个三路线战略最上层的
决策依据**——下一节会讲它具体怎么推导出"为什么要同时做三条路线"这个结论。

## 2. 这几类数据，后续具体怎么被用掉

```
靶点结构数据 ─────────────▶ 定义对接口袋(环节2/4的输入)
自建骨架+片段库 ──────────▶ 枚举出候选分子(环节3，下一节详细讲怎么拼)
DUD-E化合物+标签 ─────────▶ 不用来设计分子，倒过来检验"对接方法本身准不准"
                           (retrospective验证，当前在跑)
流行病学数据 ─────────────▶ 决定"做哪几个靶点/走哪几种机制"这个最上层问题
                           (体现在三路线架构本身，不是某一步计算)
```

要强调的是：**前三类数据服务于"怎么算"，第四类数据服务于"算什么"**。
如果没有第四类数据，这个仓库大概率会把全部精力押在路线C(直接做下一代
共价TKI打C797S)，因为这是最直觉的延续思路——正是流行病学数据显示C797S
只占6-7%、而且这条路上已经有三个真实项目在竞争，才推导出"分散到多条
收敛性更强的路线上"这个战略判断。

## 3. 分子到底怎么"设计"出来——是的，是先定整体骨架再拼，但这只是其中一种策略

你的理解是对的：这个仓库采用的策略确实是**先锁定一个骨架(scaffold，
分子的核心不变部分)，再往骨架上几个预先定义好的"可变位点"分别挂上不同
的小片段(R基团)，组合出一批候选**。[12-worked-example-walkthrough.md](12-worked-example-walkthrough.md)
第一步完整演示过这个真实拼接过程(RTC-0000怎么从骨架`[1*]c1ccc(...)...`
+ 三个真实片段`*S(C)(=O)=O`/`*C`/`*N1CCOCC1`拼出来)，这里不重复，只把
这个策略放进更大的图景里，讲清楚它是不是唯一的做法。

真实药物化学里，设计新分子的策略至少有四种，各有不同的权衡：

| 策略 | 怎么做 | 优点 | 缺点 | 本仓库用的是哪个 |
|---|---|---|---|---|
| **骨架+R基团枚举**(本仓库用的) | 先定一个骨架，枚举周边可变位点的组合 | 化学上好合成、好做构效关系(SAR)分析，计算上极便宜(纯组合+规则打分) | 如果骨架本身选错了，换多少R基团都救不回来——天花板被骨架锁死 | ✅ |
| **从头生成(de novo design)** | 不预设骨架，用算法(传统基于片段生长算法，或现代生成式AI模型)直接在口袋三维空间里"生长"出全新结构 | 不受骨架先入为主的限制，有机会找到完全意料之外的结构 | 生成的结构可能很难合成，需要额外的合成可行性过滤，计算代价也更高 | ❌ 没用 |
| **虚拟筛选现有化合物库** | 不设计新分子，直接拿几百万个已经存在、能买到的分子去对接筛选 | 起点是已知能合成、能买到的东西，工程风险最低 | 创新性完全受限于库里已经有什么，可能筛不出真正高活性的 | ❌ 没用(但`doc/11`建议的retrospective验证本质上是这类思路的"反过来用") |
| **片段生长(FBDD)** | 从一个很小的、结合很弱的片段开始，先用晶体学/NMR确认它真的占住口袋某个子位点，再一步步往外"长" | 每一步都有真实结构数据验证，不容易走偏 | 必须配合真实湿实验(晶体学)反复验证，纯计算做不了，耗时耗钱 | ❌ 没用(本仓库没有晶体学能力) |

**为什么本仓库选第一种**：这不是"唯一正确的做法"，是在"本仓库的真实目标
是跑通整套计算方法论，不是真的要产出一个能推进临床的分子"这个前提下，
性价比最高的选择——骨架+R基团枚举需要的输入(一个骨架SMILES + 几个片段
SMILES列表)是最简单、最容易用代码批量生成和筛选的数据结构，不需要任何
GPU、生成式模型或湿实验室，就能把"枚举→标准化→ADMET→决策"这整条链路
真实跑通。这和[doc/11](11-industrial-gap-and-roadmap.md)的定位判断完全
一致：**这个仓库目前是一个"早期计算假设生成器"，用最便宜的设计策略把
方法论跑通，不代表一个真实项目必须用这个策略**——如果真的要推进到可以
考虑合成的阶段，往上面表格里其他三种策略(尤其是从头生成或虚拟筛选现有
可购库)升级是完全合理的下一步，这属于[doc/11第5节](11-industrial-gap-and-roadmap.md)
路径B里"找真正的药物化学家review"这一步要重新评估的内容。

## 4. 完整设计思路：奥希替尼耐药之后，为什么是这三条路线

把前面几节串起来，这是一条完整的推导链：

**第一步，流行病学事实**：奥希替尼耐药不是单一机制，是碎片化的——
C797S突变只占6-7%，MET扩增、HER2扩增各占约10-15%，还有约50%查不出明确
的基因组驱动因素。

**第二步，这个事实否定了"只做下一代共价TKI"这个最直觉的延续思路**：
如果只盯着C797S这6-7%做下一代TKI(路线C最初的唯一方向)，天花板很低——
而且核查发现这条路线竞争已经很激烈(silevertinib/tigozertinib/BBT-176
三个真实项目同时在跑)，其中silevertinib甚至已经公开披露了本该是这条
路线护城河的CNS渗透真实数据，说明这个技术壁垒已经被头部选手攻破了一部分。

**第三步，推导出"收敛"这个战略原则**：碎片化的战场上，赢的策略是找
一个能同时覆盖多个耐药分片的"收敛点"，而不是去抢某一个小分片、在同一个
"口袋"里继续打补丁。这个原则直接推导出三条路线，每条对应一种不同层次
的"收敛"逻辑：

- **路线A(SHP2/SOS1变构抑制剂)**：收敛点在**下游信号通路**——不管是
  MET扩增、HER2扩增还是其他哪个上游受体重新被激活，最终都要经过
  RAS-MAPK这条通路才能驱动增殖，掐住这个共同的下游节点，理论上能同时
  管住所有走这条通路的耐药机制，合计覆盖约25-30%的耐药病人。
- **路线B(突变选择性EGFR降解剂)**：收敛点在**作用机制本身**——不是
  "占据某个特定位点"而是"直接把整个蛋白质降解掉"，不挑具体是哪个突变，
  理论上能同时覆盖C797S和其他靶上突变，还顺带绕开了可逆/共价抑制剂都要
  面对的"药物浓度必须压过细胞内毫摩尔级ATP浓度"这个共同难题。代价是
  CNS渗透这个真实短板，以及三元复合物预测这个计算化学前沿问题(这正是
  这次会话花大量精力去搭建、最后诚实承认"轻量版采样策略行不通"的那部分)。
- **路线C(四代EGFR TKI)**：直接狙击最大的单一已知机制(C797S 6-7%)，
  技术路径最成熟、工程实现最完整，但护城河已经被证实比预期浅。保留它的
  理由不是"赌它能赢"，是它是目前唯一有完整端到端计算管线实现的路线，
  可以当成验证整套方法论(标准化/枚举/打分漏斗/ADMET/决策引擎/DMTA回传)
  的参照实现——路线A/B复用的正是这套共享引擎(`core/`)。

**第四步，三条路线共用同一套计算引擎，只有配置不同**：这不是预先设计
好的架构，是做完路线C之后再扩展A/B时发现的事实——标准化/枚举/ADMET/
合成可及性/决策/DMTA回传这六个环节完全不依赖具体靶点是什么，只有结构
系综和打分漏斗里"口袋配置"这部分是路线专属的，所以三条路线能用同一套
`core/`代码，区别只在于`routes/<route_id>/config/`下的配置文件
(详见[doc/10第1节](10-pipeline-walkthrough.md#1-整体架构三层谁依赖谁))。

**第五步，一条贯穿所有路线的额外原则**：从第一天起按"联用"设计，不要
按"单药"设计——一线奥希替尼耐药后已经不存在单药能赢的局面(amivantamab+
化疗是现在的标准治疗)，所以三条路线的`target_profile.yaml`都新增了CYP
药物相互作用风险、与常用联用药物不重叠的毒性谱、给药方案兼容性这三项
TPP(目标产品画像)指标，不是事后补充，是从立项分析阶段就确定的约束。
