# 和工业级管线的真实差距，以及接下来具体要做什么

这篇文档回答你的两个问题："这个项目和工业界真实的计算药物研发差多少"，
以及"我接下来该怎么做"。尽量不说空话，每一条差距尽量给出"差距具体体现在
哪、为什么工业界要这么做、这对你意味着什么"。

## 1. 先说清楚：这个项目已经做对的事情

列这个不是自我表扬，是因为后面讲差距的时候，你需要知道哪些地方不用重做：

- **诚实边界**：凡是本环境算不出来的结果(没有GPU、没有商业软件、没有真实
  实验数据)，全部返回`ok=False`+具体缺什么，不编造"看起来合理"的假数值。
  这条原则本身就是工业界非常看重、但很多学术/业余项目反而做不到的基本
  纪律——真实制药公司的内部工具链里，"模型不知道自己不该信"是审计时最常
  被挑出来的问题之一。
- **真实验证过的部分确实是真的**：5EHR/6LUD/4TZ4都是真下载的晶体结构，
  Vina对接是真跑出来的分数(不是姊妹项目那个"cp文件改后缀导致全部输出
  0.0"的典型反面教材)，PyRosetta突变+repacking是真算的能量，E3配体的Ki
  是真查文献核对过的。这个"验证链路完整、每一步可追溯"的习惯，恰恰是工业
  界合规要求(数据溯源)的雏形。
- **共享引擎+路线专属配置**的架构，是真实制药公司内部CADD(计算机辅助药物
  设计)工具通常也会走的方向——不会给每个项目重写一套对接/ADMET代码，而是
  一套引擎配不同的靶点配置。
- **测试覆盖**(127个单测)覆盖了所有"纯逻辑、不需要外部基础设施"的判定函数——
  这个覆盖率在真实制药软件工程里也是会被要求的基本线。

## 2. 核心差距一句话总结

工业界计算药物研发管线真正的价值，不在"算得多准"，而在**"算 → 合成 → 测 →
拿真实数据回头校准算法 → 再算"这个闭环能不能真正转起来，而且越转模型越准**。
本仓库目前能转的是"算 → 算 → 算"——所有判定逻辑的正确性都是用**合成/演示
数据**验证的("逻辑对不对")，没有一步是用**真实湿实验数据**验证过("预测准
不准")。这是全部其他差距的根源，下面逐项展开。

## 3. 逐维度差距表

| 维度 | 本仓库现状 | 工业界真实做法 | 差距的后果 |
|---|---|---|---|
| **实验反馈闭环** | 完全没有——`core/feedback.py`的DMTA回传逻辑是真实、可测试的代码，但从未被真实湿实验数据喂过 | 每一轮计算设计出几十个分子，真的合成、真的测IC50/Kd/细胞活性，预测vs实测的误差直接决定下一轮怎么调模型 | **这是最大的差距，也是唯一一条"不花钱花时间就补不上"的差距**。没有这个闭环，本仓库里任何一个打分函数"准不准"这个问题永远无法回答，只能回答"逻辑对不对" |
| **算力规模** | 单台Mac，Vina是唯一真跑通的重计算，MD/FEP全是诚实占位 | 内部或云GPU集群(数十到数百张A100/H100量级)，FEP map(50个分子的两两微扰)常规是200-400 GPU小时 | L3(MD稳定性筛)/L4(FEP)两级完全跑不了，漏斗实际只做到L1-L2(对接)，精度天花板卡在±2.5~2.0 kcal/mol这一级 |

| **ADMET/毒性模型** | 规则引擎(SMARTS结构警示)+简单物化描述符的desirability打分，hERG是粗代理指标 | 基于内部几十万到上百万化合物的真实实验数据训练的机器学习/深度学习ADMET模型，持续用新数据再训练 | 本仓库的ADMET判断本质是"经验规则+公开知识"，没有专有数据支撑的预测能力，准确度明显低于工业界内部模型 |
| **IP/FTO(自由实施空间)** | `patent_landscape.yaml`明确标注`placeholder_not_real` | 专利代理人/律师做真实的专利检索+freedom-to-operate法律意见 | 任何基于本仓库骨架库做出的"候选分子"，**完全没有做过专利风险排查**，不能当成真实可推进的化合物，只是illustrative_only的演示结构 |
| **团队/专业分工** | 一个人+AI辅助 | 典型一个项目组：药物化学家(分子设计)、计算化学家(建模)、结构生物学家(晶体学)、DMPK科学家(药代动力学)、毒理学家、生物统计学家，外加项目管理，少则10人多则50+ | 本仓库里"骨架选不选得对""口袋片段库是不是真的合理"这类需要领域专家judgment的判断，目前全靠查文献交叉验证，没有真正的药物化学家审过 |

## 4. 这些差距里，哪些是"花钱花时间能补"，哪些是"结构性差距"

- **能补的**：算力(云GPU按需租，不需要自建集群，几百美元就能跑一次真实的
  FEP map)、力场验证(用公开的ChEMBL/BindingDB数据做retrospective验证，
  完全免费，纯计算时间)、IP检索(花几千美元找专利代理人做一次真实FTO)、
  专家review(找一两个真正的药物化学家/计算化学家做顾问性质的review)。
- **结构性的**(单靠一个人、不组建团队/不进实体实验室就补不上)：实验反馈
  闭环(需要真的有化合物被合成、被测活性)、晶体学产能、团队化分工、GLP
  合规体系、体内毒理。这些是"要不要把这个项目升级成一个真正的药物研发
  项目"这个决策本身要面对的现实，不是代码或算法能解决的。

## 5. 接下来具体怎么做：按你的目标分两条路

### 路径A：这是个人学习/技术作品集项目(如果没打算真的推进成药)

优先级从高到低：

1. **补一次retrospective验证——这是性价比最高、最该优先做的下一步**。
   去ChEMBL或BindingDB下载EGFR(或SHP2/SOS1)已知的真实活性化合物数据
   (有真实IC50/Ki的，强效和弱效都要有)，用本仓库现有的Vina对接流程把
   这批已知化合物都对接一遍，算一下对接分数和真实活性的**排序一致性**
   (Spearman相关系数)或者**区分能力**(把"强效/弱效"二值化，算ROC曲线下
   面积AUC)。这件事完全不需要新增任何基础设施，`core/docking.py`已经能跑，
   缺的只是"拿已知答案的数据集去测一次模型本身准不准"这一步——目前整个
   仓库里唯一缺的、但技术上完全可以补的环节正是这个。

   **这一步已经真实跑完，结果见[14-retrospective-validation-results.md](14-retrospective-validation-results.md)**：
   用DUD-E的EGFR数据集(542个真实活性化合物+2000个诱饵分子)跑了一遍，
   AUC=0.69(弱到中等的区分能力，比随机好但没有好很多)，EF@top1%=3.56倍。
   结论是"有保留地通过"——Vina在EGFR上不是瞎猜，但也远没到能精细排序的
   程度，验证了"L1对接只能用来粗筛，不能用来精排"这条设计原则本身是对的。
2. **路线B的采样策略**：要么实现一个真正的系统性搜索(可以尝试直接装
   PatchDock可执行文件，看macOS兼容性；或者用现成的PyMOL/RDKit写一个简化
   版的表面形状互补打分，不需要完整复刻PRosettaC)，要么诚实承认这条路线
   在当前算力/工具下走不通，写进文档作为明确的已知限制，不要为了"看起来
   完整"硬凹一个不可信的结果。
3. **技术债清单**(不需要新基础设施，纯代码改进)：
   - `clogd_approx`接入真实的pKa预测器(比如开源的`chemaxon`替代品，或者
     自己拟合一个简单的pKa经验模型)，替换掉目前直接复用`clogp`的近似。
   - 路线B的`compute_cns_mpo()`目前硬套传统小分子(MW<500)校准的desirability
     曲线在PROTAC分子上，会系统性打低分——需要专门针对beyond-Rule-of-5
     分子重新校准(文献里有一些PROTAC专属的渗透性评分方法可以参考)。
   - 给对接/PyRosetta这类需要`.venv310`才能跑的真实计算路径补上CI层面的
     回归(目前只手动验证过一次，没有自动化防止未来改坏)。
4. **如果想继续加深理解**：建议的学习方向——分子对接方法的统计验证(ROC/AUC、
   富集因子enrichment factor这类虚拟筛选评估指标)、FEP的理论基础(自由能
   微扰的统计力学推导，Zwanzig公式、BAR方法)、如果对蛋白质设计感兴趣可以
   深入PyRosetta官方教程(Rosetta Commons有免费的notebook教程)。这些比
   继续往这个仓库里加新功能更能提升你对这个领域本身的理解。

### 路径B：如果真的想推进成有机会变成真实药物的项目

这条路径意味着这个仓库的角色要从"主产品"变成"早期假设生成器"，后续重点
不在代码，在现实世界的资源和关系：

1. **先做路径A的第1步**(retrospective验证)——不管走哪条路径，这一步都是
   必须的，而且是免费的，没理由跳过。
2. **找真正的领域专家**：哪怕只是顾问性质，找一位真正的药物化学家/计算
   化学家review一下骨架选择、口袋片段库是不是真的合理，这比自己再看多少
   文献都管用——现在的`illustrative_only`标注就是在等这一步。
3. **把实验闭环哪怕只跑一次**：找学术合作实验室或CRO(合同研究组织)，
   哪怕只合成+测5-10个化合物的真实活性数据，拿这几个数据点去对比"模型
   预测的排序"和"真实测出来的排序"，这一次对比带来的信息量比继续优化
   计算方法本身大得多——没有这一步，之前所有的"判定逻辑"都只是自我验证。
4. **真实FTO**：花钱找专利代理人对最有希望的几个骨架做一次真实的专利
   检索，这个决定应该在投入更多计算资源之前做，不是之后——如果骨架本身
   有专利风险，后面算得再准都没用。
5. **认清规模现实**：从这一步到IND申报，是一个需要数千万美元、多学科
   团队、3-6年时间的项目。一个人+AI能做的，是把"最早期、最便宜的计算假设
   生成"这一步做扎实，然后把结果带给真正有能力承接后续阶段的团队/机构
   (学术实验室、创业公司、现有药企的早期研发部门)，不是一个人把整条管线
   走完。

## 6. 一句话总结

这个仓库目前是一个**设计严谨、工程纪律好、但完全没有被真实世界数据检验过**
的计算假设生成器——它的价值在于"用严肃的方法论快速产出一批值得进一步验证
的候选想法"，不在于"算出来的分数本身可以直接信"。下一步最该做的一件事
不是添加新功能，而是用公开的已知活性数据给现有方法做一次迟到的"这把尺子
到底准不准"的测验。
